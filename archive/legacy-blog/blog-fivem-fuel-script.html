FiveM Fuel Script — server-authoritative, secure, QBCore/ESX-friendly guide

Updated September 2026 · 8 min read · Stellar AI

This guide walks you step-by-step through building a robust, server-authoritative fuel system for FiveM. It covers architecture, code you can install, integration notes for QBCore/ESX, security and persistence, and a practical checklist to validate your resource.

Implementation plan (short)

1) Create a simple resource with config, client and server files. 2) Keep fuel state server-side keyed by plate (or plate+cid) and expose safe events. 3) Let the client display HUD and interact with pumps/jerrycans but never authoritatively set fuel. 4) Add persistence hook for MySQL or an export for datastore. 5) Integrate with qb-target/ox_target and item checks for refuel.

Assumptions and framework dependencies

  • Server runs FiveM with either QBCore or ESX available. Code uses conditional checks to support both.
  • You have a database resource (MySQL-async / oxmysql) if you want persistence — persistence calls are optional hooks.
  • qb-target or ox_target is optional for pump interaction; otherwise use a simple proximity check.
  • This guide uses plate-based keys. If your server has duplicated plates consider combining plate+candidate owner id (cid) for uniqueness.

High-level architecture

Keep authoritative state and validation on the server. Clients request fuel updates and the server decides whether to accept them. The client handles HUD, animation, and local smoothing (interpolation) but not permanent state changes. When persistence is enabled the server writes the fuel level to your DB on safe intervals and on player disconnect.

Why server authority matters

All critical actions (fuel deduction, refuelling, item consumption) must be validated server-side to prevent weaponized clients or speed hacks from setting fuel arbitrarily. Client-side should be treated as display-only and input provider.

Complete, destination-labelled files

Create a resource folder named fivem-fuel-script with these files. Below are minimal, deployable files: fxmanifest.lua, config.lua, server/main.lua, client/main.lua.

fxmanifest.lua

fx_version 'cerulean'
game 'gta5'

author 'YourName'
description 'Server-authoritative fuel script (QBCore/ESX friendly)'
version '1.0.0'

shared_script 'config.lua'
server_script 'server/main.lua'
client_script 'client/main.lua'

dependencies {
  -- optional: 'qb-core', 'es_extended', 'oxmysql', 'qb-target'
}

config.lua

Config = {}
Config.DefaultFuel = 70.0 -- starting fuel percentage
Config.PersistInterval = 600000 -- 10 minutes
Config.MaxFuelIncreasePerSecond = 0.5 -- validate refuel rate
Config.RefillStations = { -- example coordinates for pumps
  {x=263.0, y=260.0, z=105.0}
}
Config.UseQBCore = true -- set to false if using ESX

server/main.lua

local Fuel = {} -- fuel[plate] = {level=number, lastChange=os.time(), owner=playerId}
local lastPersist = os.time()

RegisterNetEvent('fivem-fuel:requestFuel')
AddEventHandler('fivem-fuel:requestFuel', function(plate)
  local src = source
  if not plate or type(plate) ~= 'string' then return end
  Fuel[plate] = Fuel[plate] or { level = Config.DefaultFuel }
  TriggerClientEvent('fivem-fuel:updateFuelClient', src, plate, Fuel[plate].level)
end)

RegisterNetEvent('fivem-fuel:attemptConsume')
AddEventHandler('fivem-fuel:attemptConsume', function(plate, newLevel)
  local src = source
  if not plate or type(newLevel) ~= 'number' then return end
  local now = os.time()
  Fuel[plate] = Fuel[plate] or { level = Config.DefaultFuel, lastChange = now }
  local stored = Fuel[plate]

  -- simple anti-cheat: do not accept impossible refill jumps
  local dt = math.max(1, now - (stored.lastChange or now))
  local maxIncrease = Config.MaxFuelIncreasePerSecond * dt
  if newLevel - stored.level > maxIncrease then
    -- suspicious increase, reject and log
    print(('fivem-fuel: suspicious refill by %s (plate=%s): %.2f -> %.2f'):format(src, plate, stored.level, newLevel))
    TriggerClientEvent('fivem-fuel:syncFuel', src, plate, stored.level)
    return
  end

  stored.level = math.max(0, math.min(100, newLevel))
  stored.lastChange = now
  -- optionally persist: call your DB here (safe-write)
  -- Example: exports.oxmysql:update(...) or MySQL.Async.execute(...)
end)

-- periodic persistence hook
Citizen.CreateThread(function()
  while true do
    Citizen.Wait(60000)
    if os.time() - lastPersist >= (Config.PersistInterval/1000) then
      lastPersist = os.time()
      -- iterate Fuel and write to DB safely, or export for other resources
      -- for plate, data in pairs(Fuel) do ... end
    end
  end
end)

client/main.lua

local currentFuel = nil

-- ask server for fuel on entering a vehicle
Citizen.CreateThread(function()
  while true do
    Citizen.Wait(1000)
    local ped = PlayerPedId()
    if IsPedInAnyVehicle(ped, false) then
      local veh = GetVehiclePedIsIn(ped, false)
      if veh ~= 0 then
        local plate = GetVehicleNumberPlateText(veh)
        if plate and plate ~= '' then
          TriggerServerEvent('fivem-fuel:requestFuel', plate)
        end
      end
    end
  end
end)

RegisterNetEvent('fivem-fuel:updateFuelClient')
AddEventHandler('fivem-fuel:updateFuelClient', function(plate, level)
  currentFuel = { plate = plate, level = level }
  -- update HUD display with currentFuel.level
end)

-- send fuel consumption to server periodically (server decides acceptance)
Citizen.CreateThread(function()
  while true do
    Citizen.Wait(2000)
    if currentFuel then
      local ped = PlayerPedId()
      if IsPedInAnyVehicle(ped, false) then
        local veh = GetVehiclePedIsIn(ped, false)
        local speed = GetEntitySpeed(veh) * 3.6
        -- simple consumption model
        local consume = math.max(0.01, (speed / 1000) * 2)
        currentFuel.level = math.max(0, currentFuel.level - consume)
        TriggerServerEvent('fivem-fuel:attemptConsume', currentFuel.plate, currentFuel.level)
      end
    end
  end
end)

Integration notes for QBCore/ESX/ox_lib

  • Use QBCore/ESX player identifiers to combine plate + cid for uniqueness when saving to DB.
  • If using qb-target or ox_target, expose a server-only callback for a pump action and verify player's proximity and item ownership server-side before allowing refuel.
  • Consume items (jerrycan) by invoking framework functions serverside: QBCore.Functions.RemoveItem or ESX.RemoveInventoryItem.

Practical checklist before production

StepAction
1Install resource folder into resources/[yourcategory]/fivem-fuel-script and start it in server.cfg
2Set Config.UseQBCore to match your framework and wire persistence to your DB
3Test fuel sync: enter vehicle, ensure HUD shows server-provided value
4Test refuel via pump: ensure server-side validation approves only valid refuels
5Run cheat test: attempt rapid, large fuel increases client-side and verify server rejects

Security and validation considerations

  • Never accept raw client fuel values without rate-limiting or delta checks. Use Config.MaxFuelIncreasePerSecond.
  • Always verify refuels originate from an allowed source: a pump ID or valid item consumption. Validate on server by checking player inventory or a pump-server registry.
  • Log suspicious events server-side and optionally notify admins. Don’t expose logs to clients.

Persistence and DB notes

Persist fuel to the DB at safe intervals and on player disconnect. Save by identifier (plate or plate+cid) and avoid per-second writes. Use a queue or batch writes to minimize DB load. If using oxmysql or MySQL-async, implement parameterized queries — do not concatenate user data into SQL strings.

Testing and validation steps

  1. Start server with only essential resources and this fuel resource. Confirm no runtime errors.
  2. Drive normally and verify fuel decreases and server events show expected values.
  3. Attempt to set fuel via client triggers — ensure server rejects impossible deltas.
  4. Test persistence by restarting server and confirming saved fuel loads.

Next steps and extensions

  • Expose admin commands to set/reset fuel safely server-side.
  • Integrate with vehicle keys/ownership systems to tie fuel to owner vs. plate.
