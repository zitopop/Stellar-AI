Common FiveM Errors Guide — Troubleshoot Fast and Fix Right

Updated September 2026 · 8 min read · Stellar AI

This guide helps builders diagnose and fix the most common FiveM errors fast. It focuses on authoritative troubleshooting: reading logs, fixing resource start issues, validating server calls, and avoiding client-side trust mistakes. Use the checklist and code examples to prevent repeat issues.

Why this guide

FiveM servers combine CFX runtime, Lua scripts, dependencies (QBCore, ESX, ox_lib), and external systems (MySQL, Redis). Small mismatches or missing validation often cause runtime failures. This guide helps you find root causes and implement safe fixes so resources start and stay stable in production.

1. Always start with the logs

The server console and server.log show the first symptom. Look for these patterns: resource failed to start, missing exports, Lua syntax errors, or unhandled exceptions. When a resource doesn't start, the console often prints the filename and a stacktrace—use that to pinpoint the file and line number.

2. Resource fails to start: fxmanifest and file layout

Common causes: typos in fxmanifest.lua, incorrect server_script/client_script entries, or missing files. Keep the manifest minimal and explicit. Example minimal fxmanifest for QBCore-compatible resource:

fx_version 'cerulean'
game 'gta5'

author 'you'
description 'Example resource'
version '1.0.0'

shared_script 'config.lua'
server_script 'server/main.lua'
client_script 'client/main.lua'

dependencies {
  'qb-core'
}

If the manifest references files that don't exist, the resource will not start. Check file names and case sensitivity on Linux hosts.

3. Client / Server event mismatches

Many runtime errors come from wrong event names or calling client-only APIs on the server. Remember: server scripts run in the server context and must perform authoritative checks. Client scripts should never grant items, money, or permissions without a secure server callback.

Pattern to avoid: client directly giving items. Instead, client triggers a server event, and server validates and applies the change.

Safe server-authoritative flow (QBCore-style)

-- server/main.lua
local QBCore = exports['qb-core']:GetCoreObject()

RegisterNetEvent('myresource:giveItem', function(itemName, count)
  local src = source
  -- Validate
  if type(itemName) ~= 'string' or type(count) ~= 'number' then return end
  local Player = QBCore.Functions.GetPlayer(src)
  if not Player then return end
  -- Server adds the item (authoritative)
  Player.Functions.AddItem(itemName, count)
end)

-- client/main.lua
-- request from UI or input
TriggerServerEvent('myresource:giveItem', 'bread', 1)

Note: APIs like QBCore.Functions.GetPlayer vary by QBCore versions — check your core release. For ESX, use the ESX.GetPlayerFromId pattern on the server.

4. Database and MySQL issues

Common DB mistakes: forgetting to run migrations, using blocking calls on the client, or not handling query failures. Always run SQL migrations before starting the resource and check that your DB connection string is correct. Use asynchronous wrappers like oxmysql or ghmattimysql and handle callbacks or promise rejections.

If a query fails, log the error and return a safe default to the caller. Never assume a DB call succeeded.

5. Dependency and export errors

Exports fail when a resource is not started or the export name changed. If your script depends on qb-target, ox_lib, or a particular core, declare that in fxmanifest dependencies and check server console for "missing dependency" messages. For exports, call them only after the resource is running or use a retry/backoff strategy.

6. NUI and CEF problems

NUI (CEF) issues often look like blank UIs, JS errors, or CORS-like failures. Common causes: wrong setNuiFocus usage, NUI message names mismatch, or missing HTML files in the resource. Use the browser console (F8) to inspect NUI errors and ensure you post messages using the correct event names.

7. Permissions, rate limits, and anti-cheat false positives

Anti-cheat or rate-limiters can block legitimate actions. If players report actions being blocked, check server-side rate limiting for spamming net events and ensure anti-cheat lists aren't too aggressive. Log decision points so you can reproduce and tune thresholds.

8. Reproducible debugging workflow

  1. Reproduce locally in a minimal server with only the resource and core to isolate failures.
  2. Read server console errors and follow the stacktrace to the file/line.
  3. Add defensive logging to suspect functions (source, args, validation outcome).
  4. Fix a small change, restart the resource, and test the exact failing action.
  5. Push the minimal fix and document the change in your changelog.

Practical checklist

Error Likely cause Quick fix
Resource won't start fxmanifest typo or missing file Check manifest paths, file case, and console stacktrace
TriggerServerEvent has no effect Server event name mismatch or missing registration Verify RegisterNetEvent name and log the source on server
DB queries fail Wrong DB connection, missing migrations Confirm DB credentials, run migrations, handle errors
NUI blank HTML missing or JS error in browser console Open F8, inspect console, ensure files exist in resource

Final notes

Always prefer server-side validation to prevent exploits. Keep third-party dependencies updated, test resources in a minimal environment, and use structured logging so you can trace issues quickly. When in doubt, reproduce the failure locally and add defensive checks before merging changes to production.
