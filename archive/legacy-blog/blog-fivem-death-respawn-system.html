FiveM Death & Respawn System — Server-Authoritative Design (QBCore & ESX)

Updated September 2026 · 8 min read · Stellar AI

Implementing a robust death and respawn system requires clear separation between client detection and server authority. This guide walks you from design to complete resource files, covers QBCore and ESX validation, and gives a practical checklist for testing and security.

Overview

A good FiveM death and respawn system keeps the server in control of critical actions (revive, respawn location, penalties) and keeps the client responsible for local presentation (ragdoll, camera). This reduces cheating risk and ensures consistent behavior across frameworks like QBCore and ESX. The example below is a compact resource that implements: death detection, server-side logging and validation, timed respawn, ambulance job revives, and a simple player-requested respawn flow.

Implementation plan (short)

  1. Detect player death on the client and send a single server event with location & cause.
  2. Server records state and enforces respawn rules (timer, job-only revives, costs).
  3. Server triggers validated revive/respawn client events.
  4. Client handles UI and final local respawn (NetworkResurrectLocalPlayer + SetEntityHealth).

Assumptions & framework dependencies

  • Server is authoritative: all revives/respawns are triggered by server events.
  • You either have QBCore (exports['qb-core']:GetCoreObject()) or ESX (esx:getSharedObject) available. The examples include conditional snippets for both.
  • Do not rely on client trust for job checks, money deductions, or distance checks—perform those on server.
  • Client will show UI/menus but cannot execute revives directly.

Files provided (destination-labelled)

This example is a ready-to-drop resource named death_system. Place files under resources/[local]/death_system/ and add to server.cfg with ensure death_system.

fxmanifest.lua

game 'gta5'

shared_script 'config.lua'
client_script 'client.lua'
server_script 'server.lua'

config.lua

Config = {}
Config.RespawnTime = 90 -- seconds until automatic respawn
Config.ReviveDistance = 5.0 -- max distance (meters) for ambulance revive validation on server
Config.AllowSelfRespawn = true -- allow player-requested respawn after timer
Config.Framework = 'qb' -- set to 'qb' or 'esx'

server.lua

local framework = Config.Framework

if framework == 'qb' then
  QBCore = exports['qb-core']:GetCoreObject()
else
  ESX = nil
  TriggerEvent('esx:getSharedObject', function(obj) ESX = obj end)
end

local deadPlayers = {} -- src -> {x,y,z,deathTime}

RegisterNetEvent('deathsystem:playerDied', function(data)
  local src = source
  if not data or not data.pos then return end
  -- basic anti-spam: only allow a death record if not already dead
  if deadPlayers[src] then return end
  deadPlayers[src] = {pos = data.pos, time = os.time()}
  print(('death_system: player %d died at %.2f %.2f'):format(src, data.pos.x, data.pos.y))
  -- notify EMS, log to database (implementers: do DB on your side)
end)

RegisterNetEvent('deathsystem:requestRevive', function(targetSrc)
  local src = source
  -- validate caller is ambulance
  local jobName
  if framework == 'qb' then
    local xPlayer = QBCore.Functions.GetPlayer(src)
    jobName = xPlayer and xPlayer.PlayerData.job.name
  else
    local xPlayer = ESX.GetPlayerFromId(src)
    jobName = xPlayer and xPlayer.job.name
  end
  if jobName ~= 'ambulance' then
    print(('death_system: %d attempted revive without job'):format(src))
    return
  end
  -- validate target is recorded dead
  if not deadPlayers[targetSrc] then return end
  -- distance check
  local medicCoords = GetEntityCoords(GetPlayerPed(src))
  local targetCoords = deadPlayers[targetSrc].pos
  local dist = #(vector3(medicCoords.x, medicCoords.y, medicCoords.z) - vector3(targetCoords.x, targetCoords.y, targetCoords.z))
  if dist > Config.ReviveDistance then return end
  -- all good: server triggers client revive
  TriggerClientEvent('deathsystem:reviveClient', targetSrc)
  deadPlayers[targetSrc] = nil
end)

-- automatic respawn after timer (server-side tick)
CreateThread(function()
  while true do
    local now = os.time()
    for src, info in pairs(deadPlayers) do
      if now - info.time >= Config.RespawnTime then
        TriggerClientEvent('deathsystem:forceRespawn', src, info.pos)
        deadPlayers[src] = nil
      end
    end
    Wait(5000)
  end
end)

client.lua

local isDead = false

-- simple death detection loop
CreateThread(function()
  while true do
    Wait(1000)
    local ped = PlayerPedId()
    if DoesEntityExist(ped) then
      if IsEntityDead(ped) and not isDead then
        isDead = true
        local pos = GetEntityCoords(ped)
        TriggerServerEvent('deathsystem:playerDied', {pos = {x = pos.x, y = pos.y, z = pos.z}})
        -- show local UI, ragdoll etc.
      elseif not IsEntityDead(ped) and isDead then
        isDead = false
      end
    end
  end
end)

RegisterNetEvent('deathsystem:reviveClient', function()
  local ped = PlayerPedId()
  local pos = GetEntityCoords(ped)
  NetworkResurrectLocalPlayer(pos.x, pos.y, pos.z, GetEntityHeading(ped) or 0.0, true, false)
  SetEntityHealth(ped, 200)
  ClearPedTasksImmediately(ped)
end)

RegisterNetEvent('deathsystem:forceRespawn', function(spawnPos)
  -- server-authoritative forced respawn; choose spawnPos or hospital spawn
  local ped = PlayerPedId()
  NetworkResurrectLocalPlayer(spawnPos.x, spawnPos.y, spawnPos.z, 0.0, true, false)
  SetEntityHealth(ped, 200)
  ClearPedTasksImmediately(ped)
end)

Server authority & security considerations

Always validate the following on the server:

  • Caller job and permissions (use QBCore.Functions.GetPlayer / ESX.GetPlayerFromId). Do not trust data sent by the client about job names or money.
  • Proximity when medic revives a target—check server-side positions or compare timestamps and locations recorded during death.
  • Rate-limit death events to prevent spam or griefing logs.
  • Log suspicious activity (multiple revive attempts, invalid job calls) for review.

Integration tips for QBCore and ESX

When integrating with in-server economy or missions:

  • Charge a respawn fee server-side and deduct from player money (QBCore.Functions.RemoveMoney or xPlayer.removeMoney).
  • Trigger ambulance job notifications via exports or server events (for qb-phone or esx_phone integrations).
  • Use server persistence to mark player as injured to prevent weapon use until revived.

UI & UX suggestions

Keep client UI local: a death timer, 'Request Respawn' button and 'Awaiting Medic' status are all client-side displays. When the player requests a respawn or cancels, send a single event to the server and wait for server confirmation. Avoid having client perform NetworkResurrectLocalPlayer without server permission.

Testing & validation steps

  1. Start server with the resource ensured. Confirm console logs print death events.
  2. Die in-game and confirm your client sends a single death report. Check server side deadPlayers entry.
  3. As ambulance, attempt revive within and outside Config.ReviveDistance; ensure server accepts only valid ones.
  4. Try to call revive as non-ambulance and confirm server ignores it.
  5. Wait for auto-respawn timer and confirm forceRespawn fires and client respawns.
