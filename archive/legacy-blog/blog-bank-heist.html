How to Add a Bank Heist Script to Your FiveM QBCore Server

A practical guide to how to add a bank heist script to your fivem qbcore server, with implementation decisions, validation steps, and security considerations for a production-minded project.

This guide walks through integrating a bank heist script into a FiveM QBCore server and covers architecture, implementation choices, server validation, testing, deployment, and maintenance. The same security principles are noted for ESX and Roblox (Luau) implementations where relevant. Use this as a technical plan and reference checklist for a production-grade, server-authoritative heist that resists client tampering and supports robust, maintainable behavior.

High-level architecture

Design the heist as a server-authoritative resource that coordinates state between persistent storage (database), server runtime memory, and clients. Key components:

  • Server state manager — maintains active heists, cooldowns, and saves progress to DB.
  • Server validation handlers — check job counts (police), player inventory, money distribution, and permission checks.
  • Client UI and animation layer — only shows effects and sends intent (button press, interaction) to server.
  • Third-party integrations — qb-target/ox_target or ox_lib for interactions; oxmysql or ghmattimysql for persistence.
  • Logging and monitoring — audit logs for start/stop/fail and criminal payouts.

State model and data flow

Keep authoritative data on the server and persist necessary state. Example state objects:

  • ActiveHeists: { heistId, bankId, startedAt, participants = {source,...}, stage, lootRemaining }
  • BankDefs: static config for each bank (doors, vault positions, required items, minimum cops)
  • Cooldowns: bankId -> timestamp when next allowed

Flow for a single heist action (high level):

  1. Client requests interaction (TriggerServerEvent).
  2. Server validates (player exists, items, police online, not on cooldown).
  3. Server reserves lock (mark heist active) and persists to DB if multi-minute.
  4. Server notifies clients (start UI, hide openable door to all clients, spawn loot objects server-side or instruct clients to local spawn with server validation).
  5. Server monitors events, awards money only from server-side operation when appropriate.

Implementation choices: qb-core, ESX, and libraries

Common options and recommendations:

  • Use a dedicated resource for the heist that depends on qb-core (declare in fxmanifest) rather than patching core files — easier to maintain and update.
  • Support integration with qb-target or ox_target for interaction. Provide fallback exports for other target systems.
  • Use oxmysql (or ghmattimysql) for persistent cooldowns and long-running heist state; store only what you need to reconstruct a failed or restarted heist.
  • Make core logic server-side; clients are presenters only. For animations and objects with breakable state, keep the canonical state on the server and broadcast deltas.

Key server-side validation (never trust client)

Security principles:

  • Always verify player state server-side using QBCore.Functions.GetPlayer(source) or ESX.GetPlayerFromId.
  • Check inventory and remove items server-side — do not accept client-submitted inventory changes.
  • Verify police count by iterating server-side player list and checking PlayerData.job.name == "police" and on-duty status.
  • Enforce per-bank cooldowns from server memory and persistent DB.
  • Use transaction-like patterns when awarding money — update DB and then notify the client.

Server-side starter example (QBCore)

-- server.lua (excerpt)
local QBCore = exports['qb-core']:GetCoreObject()
local activeHeists = {}
local cooldowns = {}

RegisterNetEvent('heist:start', function(bankId)
  local src = source
  local Player = QBCore.Functions.GetPlayer(src)
  if not Player then return end

  -- Validate police count
  local cops = 0
  for _, pid in pairs(QBCore.Functions.GetPlayers()) do
    local p = QBCore.Functions.GetPlayer(pid)
    if p and p.PlayerData.job and p.PlayerData.job.name == 'police' and p.PlayerData.job.onduty then
      cops = cops + 1
    end
  end
  if cops < Config.Banks[bankId].minCops then
    TriggerClientEvent('heist:notify', src, 'Not enough police online')
    return
  end

  -- Cooldown check
  if cooldowns[bankId] and os.time() < cooldowns[bankId] then
    TriggerClientEvent('heist:notify', src, 'Bank is on cooldown')
    return
  end

  -- Item check: thermite or keycard
  if Player.Functions.GetItemByName('thermite') == nil then
    TriggerClientEvent('heist:notify', src, 'You need thermite')
    return
  end

  -- Remove item server-side and start heist
  Player.Functions.RemoveItem('thermite', 1)
  activeHeists[bankId] = { startedAt = os.time(), participants = {src} }
  cooldowns[bankId] = os.time() + Config.Banks[bankId].cooldown
  TriggerClientEvent('heist:started', -1, bankId) -- broadcast
end)

Note: Player.Functions.GetItemByName is a placeholder for your inventory system's lookup; always call your actual QBCore/ESX methods.

Persistence and DB patterns

Keep the DB usage minimal and robust:

  • Save only long-running or important state: cooldowns, staged loot counts, and final payouts.
  • Use transactions or idempotent updates — avoid duplicated payouts if the server restarts mid-heist.
  • Store an audit row per finished heist (heist_id, bank, start_time, end_time, participants JSON, payout summary) for ops and rollback investigation.

DB save example (pseudo)

-- run after heist ends
local sql = "INSERT INTO heist_logs (bank, start_time, end_time, participants, loot) VALUES (@bank,@start,@end,@participants,@loot)"
exports.oxmysql:execute(sql, {
  ['@bank'] = bankId,
  ['@start'] = startedAt,
  ['@end'] = os.time(),
  ['@participants'] = json.encode(participants),
  ['@loot'] = json.encode(lootSummary)
})

Anti-cheat and hardening

Anti-cheat is both proactive and reactive:

  • Authorize all sensitive actions on the server. If a client requests "open vault," server checks and updates state.
  • Rate-limit requests from any single source. Keep per-source watchdogs in server memory.
  • Log suspicious events to a separate table or file (unexpected large payout requests, out-of-band inventory changes) for manual review.
  • Obfuscate nothing critical — securing is about server validation, not hiding logic.

Testing and QA

Create a test plan that simulates real conditions:

  • Unit tests for server validators (inventory check, police count, cooldown logic).
  • Integration tests with a dev DB: start/abort/complete flows and verify DB audit rows.
  • Load tests: simulate multiple concurrent start requests to validate race conditions and locking behavior.
  • Failover tests: simulate server restart mid-heist and ensure persistent state or safe abort behavior.

Local debug tips

  • Use verbose server logs for a dev environment only; sanitize before production.
  • Simulate low police counts and check notifications and prevent-start behavior.
  • Verify money is only minted by server code after DB updates (preferably atomic).

Deployment and maintenance

When deploying to production:

  1. Deploy to a staging server first and run automated acceptance tests.
  2. Enable a migration to add heist tables/columns in a vetted DB migration script.
  3. Monitor memory usage and activeHeists table size; clear stale entries after a safe timeout.
  4. Periodically review logs and adjust thresholds or cooldowns based on gameplay balance.

Roblox (Luau) considerations

On Roblox, the same server-authoritative rules apply but using RemoteEvents and DataStores:

  • Handle all heist state inside a server Script (ServerScriptService), using RemoteEvent: OnServerEvent to receive client intents.
  • Validate inventory/possession server-side using the server-side Player object and server-side inventory module.
  • DataStore failure handling: always pcall DataStore calls and implement retry with exponential backoff. Do not assume success — have idempotent or compensating logic.
  • Save incremental progress frequently if the heist lasts long; use UpdateAsync for atomic updates where needed.

Roblox server skeleton (Luau)

local Remote = game.ReplicatedStorage:WaitForChild('HeistRemote')

  -- Validate player, permissions, items on server

  end

Maintenance and tuning

Operational guidance:

  • Track key events (start/fail/complete) and review weekly for anomalies.
  • Keep a migration script for DB changes; maintain backwards compatibility where possible.
  • Update the heist resource when qb-core or target libs change their exported signatures — subscribe to their release notes.
  • Provide a server config UI or config file with adjustable parameters: minCops, payout ranges, cooldown length, and rewards types.
