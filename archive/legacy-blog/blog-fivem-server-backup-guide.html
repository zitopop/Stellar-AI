FiveM Server Backup Guide

Updated September 2026 · 8 min read · Stellar AI

A concrete, security-first approach to backing up FiveM resources and databases. This guide covers host-level automation, safe database dumps for QBCore/ESX, an optional admin-only in-game trigger, retention policy, and recovery testing.

Backing up a FiveM server is an operational imperative: resource files, configuration, and the player database are required to restore service after hardware failure, accidental deletion, or a failed upgrade. This guide gives a practical plan, safe scripts, server-side examples that respect authority and validation, and a tested restore checklist.

Implementation plan (short)

1) Prioritise host-level backups (filesystem + database). 2) Automate with cron or systemd and push encrypted archives offsite (S3/GCS). 3) Optionally provide an admin-only in-game trigger that requests a host-level backup via an authenticated webhook. 4) Test restores and document recovery steps.

Assumptions and dependencies

  • Your FiveM server runs on a Linux host or VM with shell access.
  • Player data is stored in MySQL/MariaDB (common for QBCore, ESX, oxmysql or ghmattimysql setups).
  • You can create a user with limited DB permissions for dumps or use a read-only dump user.
  • Backups should be managed outside of the resource folder; avoid storing secrets in the repo.

Host-level backup (recommended first)

Host-level backups are the most reliable. They can snapshot the entire FiveM directory, server.cfg, custom resources, and optionally the database dump. Use a retained, encrypted archive strategy and push archives to an offsite store.

Example bash backup script (safe, uses env file)

# /usr/local/bin/fivem-backup.sh
set -e
source /etc/fivem-backup.env # contains DB_USER, DB_PASS, DB_NAME, BACKUP_DIR, S3_BUCKET, GPG_KEY
TIMESTAMP=$(date -u +"%Y-%m-%dT%H%M%SZ")
ARCHIVE="$BACKUP_DIR/fivem-backup-$TIMESTAMP.tar.gz"
# Dump MySQL to a temporary file
mysqldump -u "$DB_USER" -p"$DB_PASS" "$DB_NAME" > /tmp/fivem-sql-$TIMESTAMP.sql
# Create archive with server files and DB dump (exclude node_modules, caches)
tar --exclude='node_modules' --exclude='cache' -czf "$ARCHIVE" /opt/fivem /etc/fivem/server.cfg /tmp/fivem-sql-$TIMESTAMP.sql
# Encrypt archive with GPG public key
gpg --encrypt --recipient "$GPG_KEY" --output "$ARCHIVE.gpg" "$ARCHIVE"
# Push to S3 (awscli configured separately)
aws s3 cp "$ARCHIVE.gpg" "s3://$S3_BUCKET/"
# Clean temporary files
rm -f "$ARCHIVE" /tmp/fivem-sql-$TIMESTAMP.sql

Notes: store DB credentials in /etc/fivem-backup.env owned by root with 600 permissions. Do not commit this file. Use a deploy key/service account for S3 upload; keep that config on the host only.

Database-only dumps for QBCore / ESX

Both QBCore and ESX rely on MySQL. A consistent dump is important; you can use mysqldump with --single-transaction for InnoDB to avoid locking, or use a logical backup tool compatible with your engine. Use a DB user limited to SELECT, LOCK TABLES (if required), and SHOW VIEW; avoid using root in automation.

Optional: Admin-triggered in-game backup (server-authoritative)

Provide an optional resource that sends an authenticated request to a host-side webhook which initiates the host backup. This keeps the heavy work off the game server process and enforces server authority. The in-game command must validate admin permissions server-side (not client-side).

Server-side resource example (fxmanifest + Lua)

-- fxmanifest.lua
fx_version 'cerulean'
game 'gta5'
author 'Ops'
server_script 'server.lua'

-- server.lua
local http_endpoint = GetConvar('backup_webhook', '') -- set in server.cfg

RegisterCommand('triggerbackup', function(source, args, raw)
  -- server-only command
  local src = source
  if src ~= 0 then
    -- player issued command: validate with framework
    local allowed = false
    -- QBCore example
    if GetResourceState('qb-core') == 'started' then
      local QBCore = exports['qb-core']:GetCoreObject()
      local xPlayer = QBCore.Functions.GetPlayer(src)
      if xPlayer and xPlayer.PlayerData.job.name == 'admin' then allowed = true end
    end
    -- ESX example fallback
    if not allowed and GetResourceState('es_extended') == 'started' then
      local xPlayer = ESX.GetPlayerFromId(src)
      if xPlayer and (xPlayer.getGroup() == 'admin' or xPlayer.getGroup() == 'superadmin') then allowed = true end
    end
    if not allowed then
      TriggerClientEvent('chat:addMessage', src, { args = { '^1Backup', 'Permission denied.' } })
      return
    end
  end
  -- server-originated or validated player: call webhook
  PerformHttpRequest(http_endpoint, function(code, res, headers) end, 'POST', json.encode({ action = 'start' }), { ['Content-Type'] = 'application/json', ['Authorization'] = 'Bearer ' .. GetConvar('backup_token','') })
end, false)

Important: Set backup_webhook and backup_token in server.cfg, not in resources. The webhook should authenticate the token and run the host backup script; never embed shell execution directly in the game process.

Testing restores and validation

Backups are only useful when regularly tested. Restore to a staging host monthly and validate: resource files load, server.cfg settings intact, and the database contains expected players. For DB restores, check user IDs, money balances, and character inventories; for frameworks, verify QBCore/ESX compatibility after restore.

Security considerations

  • Do not run backup scripts under the FiveM service account with excessive privileges.
  • Use dedicated limited DB users, encrypt backups, and employ rotating keys if possible.
  • Keep webhook tokens and cloud credentials out of resource files and put them in server.cfg or /etc environment files with strict permissions.

Monitoring and automation

Use cron or systemd timers to schedule nightly backups and a monitoring alert on failure. Keep logs of backup runs and S3/GCS upload results. Consider using a retention lifecycle rule on the cloud bucket to prune old encrypted archives automatically.

Practical checklist before going live

  1. Create /etc/fivem-backup.env and set permissions to 600.
  2. Install and test mysqldump and awscli/gcloud CLI on the host.
  3. Deploy and test the backup script manually; verify archive encryption.
  4. Push one encrypted archive to offsite storage; attempt a staged restore.
  5. Schedule cron/systemd and configure monitoring alerts for failures.
  6. If using in-game trigger, ensure tokens are in server.cfg and webhook validates token server-side.
  7. Document the restore process and store it in your ops runbook.

Automation example: cron

# Run at 03:30 daily
30 3 * * * /usr/local/bin/fivem-backup.sh >> /var/log/fivem-backup.log 2>&1

Summary

Prioritise host-level encrypted backups and offsite storage, use limited DB users for dumps, automate with cron/systemd and monitor failures, and keep an optional in-game trigger strictly server-authoritative. Test restores regularly and document the process. Following this pattern keeps your FiveM server resilient and recoverable without exposing credentials or overloading the game process.
