FiveM Bank Robbery Script — Server-Authoritative, QBCore-Friendly Guide

Updated September 2026 · 8 min read · Stellar AI

This guide walks you through building a secure, server-authoritative bank robbery script for FiveM. It explains design decisions, provides complete example files for QBCore, covers installation, and lists a practical testing checklist.

Overview

Bank robberies are high-impact gameplay features: they must feel cinematic while remaining secure and authoritative. This guide focuses on an approach that keeps critical logic on the server, validates client messages, integrates cleanly with QBCore (with notes for ESX/ox_lib), and avoids common exploits such as client-side reward minting, permission bypasses, or sync issues.

Design principles

  • Server authority: All reward, cooldown, vault state, and payout calculations run server-side.
  • Declarative config: Keep positions, timers, and rewards in a config file to allow fast tweaking.
  • Graceful failure handling: Any network or state error should abort the robbery and notify the client.
  • Minimal client trust: Client handles visuals, animation, and interaction requests only.

Short implementation plan

  1. Define config: bank locations, cooldowns, required items, police count requirements.
  2. Create fxmanifest and resource structure.
  3. Implement server.lua to manage bank state, verify dependencies, and issue payouts via QBCore.
  4. Implement client.lua to prompt interactions (qb-target or ox_target), play animations, and call the server events.
  5. Test with multiple clients and ensure robust anti-cheat checks and logging.

Assumptions & framework notes

This guide assumes a QBCore server (qb-core). For ESX, replace QBCore exports with ESX.TriggerServerCallback and ESX.GetPlayerFromId equivalents and persist server-side state similarly. If you use ox_lib or ox_target, adapt the target registration in the client to use their export names. The server examples use QBCore exports and standard FiveM events.

Files — complete example

Below are minimal but complete files to get a safe robbery started. Put these inside a resource folder named fivem-bank-robbery.

fxmanifest.lua

fx_version 'cerulean'
game 'gta5'

author 'You'
description 'Server-authoritative bank robbery example (QBCore)'
version '1.0.0'

shared_script 'config.lua'
client_script 'client.lua'
server_script 'server.lua'

dependencies {
  'qb-core'
}

config.lua

Config = {}
Config.Banks = {
  { id = 'fleeca1', name = 'Fleeca Bank', coords = vector3(148.34, -1040.22, 29.37), cooldown = 3600, rewardMin = 5000, rewardMax = 15000, requiredPolice = 2 }
}
Config.RequiredItem = 'lockpick'

server.lua

local QBCore = exports['qb-core']:GetCoreObject()
local BankState = {}

for _, bank in pairs(Config.Banks) do
  BankState[bank.id] = { onCooldown = false }
end

RegisterNetEvent('fivem-bank-robbery:attempt', function(bankId)
  local src = source
  local Player = QBCore.Functions.GetPlayer(src)
  local bank = nil
  for _, b in pairs(Config.Banks) do if b.id == bankId then bank = b end end
  if not bank then return end

  -- Basic checks
  if BankState[bankId].onCooldown then
    TriggerClientEvent('fivem-bank-robbery:notify', src, 'This bank was recently robbed.')
    return
  end

  -- Police count check (example using qb-core metadata)
  local cops = 0
  for _, player in pairs(QBCore.Functions.GetPlayers()) do
    local ply = QBCore.Functions.GetPlayer(player)
    if ply and ply.PlayerData.job and ply.PlayerData.job.name == 'police' then cops = cops + 1 end
  end
  if cops < bank.requiredPolice then
    TriggerClientEvent('fivem-bank-robbery:notify', src, 'Not enough police online.')
    return
  end

  -- Inventory / item check
  if not Player.Functions.GetItemByName(Config.RequiredItem) then
    TriggerClientEvent('fivem-bank-robbery:notify', src, 'You need a lockpick to start this robbery.')
    return
  end

  -- Mark bank in cooldown state
  BankState[bankId].onCooldown = true
  SetTimeout(bank.cooldown * 1000, function() BankState[bankId].onCooldown = false end)

  -- Secure reward: random within server bounds
  local reward = math.random(bank.rewardMin, bank.rewardMax)

  -- Final validation and payout
  -- Example: ensure player still exists and is near bank
  local playerCoords = Player.PlayerData.position
  if not playerCoords or #(vector3(playerCoords.x, playerCoords.y, playerCoords.z) - bank.coords) > 10.0 then
    TriggerClientEvent('fivem-bank-robbery:notify', src, 'You are too far from the bank.')
    return
  end

  -- Add money, log, and notify police
  Player.Functions.AddMoney('cash', reward, 'bank-robbery')
  TriggerClientEvent('fivem-bank-robbery:success', src, reward)
  -- TODO: integrate dispatch for police
end)

client.lua (interaction / qb-target)

local QBCore = exports['qb-core']:GetCoreObject()

CreateThread(function()
  for _, bank in pairs(Config.Banks) do
    exports['qb-target']:AddBoxZone(bank.id, bank.coords, 2.0, 2.0, { name = bank.id, heading = 0, debugPoly = false }, { options = {
      { event = 'fivem-bank-robbery:clientStart', icon = 'fas fa-user-secret', label = 'Rob Bank', bankId = bank.id }
    }, distance = 3.5 })
  end
end)

RegisterNetEvent('fivem-bank-robbery:clientStart', function(data)
  local bankId = data.bankId
  -- Play animation, progress bar etc.
  TriggerServerEvent('fivem-bank-robbery:attempt', bankId)
end)

Installation & deployment

  1. Place the folder fivem-bank-robbery in your resources directory.
  2. Add ensure fivem-bank-robbery to your server.cfg after qb-core.
  3. Restart or start the resource and test in a local environment before deploying to live.

Security and validation checklist

Ensure the following server-side rules are enforced to reduce attack surface:

CheckServer-side enforcement
Reward issuancePayouts only on server after all checks
CooldownsBankState table tracked on server, not client
Distance validationVerify player's position before payout
Police requirementCount police on server, do not trust client reports
Item checksVerify inventory server-side (GetItemByName)

Testing checklist (practical)

  • Test single-player robbery: verify payout, cooldown sets, and notifications.
  • Test multi-player: attempt simultaneous robberies and ensure server blocks duplicates.
  • Attempt spoofing: send attempt events from client scripts; server should still validate position, items, and police count.
  • Network failure: drop connection mid-robbery and confirm server cleans up timers as needed.
  • Edge cases: player disconnect during robbery, police count changes mid-process.

Optimization & anti-cheat notes

Keep expensive checks minimal: cache police counts with a short TTL, validate proximity against a stored vector3 rather than trusting client coordinates, and keep logs for manual review. Avoid heavy per-tick work on the server; use event-driven state transitions and timeouts.

Next steps & integration ideas

  • Integrate with a dispatch resource to notify police with blips and calls.
  • Add vault mini-games on the client, but validate success server-side with proof tokens or a server-driven RNG.
  • Connect to a logging system or webhook for auditing high-value payouts.
