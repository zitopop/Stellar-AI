ESX to QBCore Migration: A Practical, Server-First Guide for FiveM Projects

Updated September 2026 · 8 min read · Stellar AI

Migrate an ESX resource to QBCore without breaking server authority, accounts, or player data. This guide gives a realistic plan, API mappings, configuration examples, a secure server-side conversion pattern, database migration notes, and a short Roblox-oriented checklist for similar server-client concerns.

Why migrate from ESX to QBCore?

QBCore (qb-core) offers a modern API, an active community, and modular patterns such as Player objects and ox_lib utilities. Many server teams choose QBCore for clearer abstractions around items, callbacks, and permissions. Migration should be driven by long-term maintainability, not hype: plan carefully and keep the server authoritative at all times.

High-level migration plan

Follow these phased steps to avoid downtime and data loss:

  • Audit the existing ESX resource and site-wide dependencies.
  • Map ESX APIs used (callbacks, usable items, player methods) to QBCore equivalents.
  • Create a QBCore-compatible resource skeleton and fxmanifest.
  • Implement server-side conversions with strict validation and logging.
  • Migrate persistent data (inventories, money, metadata) with tested SQL transforms.
  • Deploy behind a feature flag and test with a staging server.

Assumptions and dependencies

Assume your target server uses qb-core v1+ exported GetCoreObject pattern. If you rely on ox_lib, qb-target, or other addons, document versions. If you lack the ESX database schema, export it first. Key API mappings (quick reference)

  • ESX.RegisterServerCallback -> QBCore.Functions.CreateCallback
  • ESX.RegisterUsableItem -> QBCore.Functions.CreateUseableItem
  • ESX.GetPlayerFromId(source) -> QBCore.Functions.GetPlayer(source)
  • xPlayer.addInventoryItem -> Player.Functions.AddItem
  • TriggerClientEvent/ServerEvent remain the same but validate on server

Server-side callback example (ESX -> QBCore)

ESX server callback (old pattern):

ESX.RegisterServerCallback('myresource:getBalance', function(source, cb)
  local xPlayer = ESX.GetPlayerFromId(source)
  if not xPlayer then return cb(0) end
  cb(xPlayer.getMoney())
end)

Convert to QBCore pattern with validation and nil checks:

local QBCore = exports['qb-core']:GetCoreObject()

QBCore.Functions.CreateCallback('myresource:getBalance', function(source, cb)
  local Player = QBCore.Functions.GetPlayer(source)
  if not Player then
    cb(0)
    return
  end
  -- Use Player.PlayerData.money or Player.Functions.GetMoney() depending on version
  cb(Player.PlayerData.money['bank'] or 0)
end)

Converting usable items safely

ESX.RegisterUsableItem allowed client-side triggers; with QBCore you should create useable items and perform authoritative checks server-side before granting effects.

-- QBCore: create a usable item and validate inventory server-side
QBCore.Functions.CreateUseableItem('thermite', function(source)
  local Player = QBCore.Functions.GetPlayer(source)
  if not Player then return end
  local count = Player.Functions.GetItemByName('thermite') and Player.Functions.GetItemByName('thermite').amount or 0
  if count < 1 then
    TriggerClientEvent('QBCore:Notify', source, 'You do not have thermite', 'error')
    return
  end
  -- remove one thermite, then trigger client effect
  Player.Functions.RemoveItem('thermite', 1)
  TriggerClientEvent('myresource:client:UseThermite', source)
end)

Always remove items and apply cooldowns on the server to prevent client-side exploitation.

fxmanifest and resource layout

Switch your dependency from es_extended to qb-core and follow QBCore recommended structure. Example fxmanifest snippet:

fx_version 'cerulean'
game 'gta5'

author 'YourName'
description 'MyResource migrated to QBCore'
version '1.0.0'

shared_scripts {
  '@qb-core/shared/locale.lua',
  'config.lua'
}

server_scripts {
  '@qb-core/server/main.lua',
  'server/main.lua'
}

client_scripts {
  'client/main.lua'
}

dependencies {
  'qb-core'
}

Database and persistent data migration

ESX and QBCore manage player data differently. Do not guess schema fields — inspect both schemas and write idempotent SQL transforms. Typical steps:

  1. Dump ESX player table(s) to staging.
  2. Map identifiers (steam license, identifiers) exactly.
  3. Transform inventory JSON formats if needed, testing with a single user after a backup.
  4. Write transactional SQL scripts and test rollback.

If you're unsure, start by migrating a low-risk subset (e.g., money only) and run both systems in parallel on a test server.

ox_lib, qb-target and permission boundaries

When migrating target interactions, replace ESX client-side triggers with qb-target exports or ox_target zones. Use server-side permission checks for admin commands and inventory changes. Never trust client assertions about amounts or item existence — always re-check on the server.

Roblox note: analogous server-client concerns

While Roblox is a different platform, the same server-authoritative principles apply. Use RemoteEvents/RemoteFunctions correctly and validate inputs on the server. Example Luau pattern for safe RemoteEvent handling and DataStore error handling:

-- ServerScript in Roblox
local Players = game:GetService('Players')
local DataStoreService = game:GetService('DataStoreService')
local MyDS = DataStoreService:GetDataStore('PlayerData')
local Remote = script:WaitForChild('SaveRequest') -- RemoteEvent

Remote.OnServerEvent:Connect(function(player, data)
  -- validate structure and types
  if type(data) ~= 'table' then return end
  local success, err = pcall(function()
    MyDS:SetAsync('p_' .. player.UserId, data)
  end)
  if not success then
    warn('DataStore Save failed for', player.UserId, err)
    -- consider retry logic or queueing
  end
end)

Apply similar validation and retry/backoff strategies when moving persistent data between game frameworks.
