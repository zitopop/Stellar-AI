FiveM Heist Script Guide

Updated September 2026 · 8 min read · Stellar AI

This guide walks you through planning, building, and hardening a FiveM heist script. It uses QBCore-flavoured examples, explains server-authoritative patterns, offers deployment checks, and points to tools to accelerate iteration.

Overview

Heist scripts are complex: multiple players, staged progress, rewards, and interactions with police systems and anti-cheat. The core rule is simple: never trust the client. Keep all game-changing logic server-side, validate every reward and state transition, and make your client responsible only for visuals, inputs, and local prediction. This guide outlines a pragmatic design, example files (fxmanifest.lua, server.lua, client.lua), and a checklist you can follow to launch a robust heist resource.

Design principles

  • Server authority: Server owns heist state, cooldowns, rewards, and police counts.
  • Minimal client trust: Client sends intent (start/complete action), server verifies prerequisites.
  • Fail safe and logging: Log critical transitions and failure reasons to detect abuse.
  • Config-driven: Keep numbers (rewards, durations, police required) in a server-side config file.
  • Pluggable targets: Implement generic hooks so resources like qb-target or ox_lib can be optional integrations.

Dependencies and assumptions

Example code below uses QBCore (commonly used in many servers). If you use ESX or a different framework, adapt player money/item calls. Assumptions:

  • QBCore is available as a server export (QBCore = exports['qb-core']:GetCoreObject()).
  • qb-policejob or a job-counting system exists to enforce required cops online.
  • qb-target or an alternative targeting system may be present but is optional.

File layout

A small, clear structure reduces mistakes. Place these files inside a resource named heist_resource:

PathPurpose
fxmanifest.luaResource manifest
config.luaServer-side configuration (cooldowns, rewards)
server.luaAuthoritative logic, validation, events
client.luaPlayer interactions, animations, progress UI
html/*Optional UI for progress and timers
README.mdInstall and admin info

Core server example (server.lua)

Keep reward granting, cooldowns, and police checks on the server. Below is a minimal but safe pattern using QBCore functions and server-side validation.

local QBCore = exports['qb-core']:GetCoreObject()
local Heist = {active = false, cooldown = 0}

-- Read from shared config
local REQUIRED_COPS = Config.RequiredCops
local COOLDOWN = Config.CooldownSeconds
local REWARD = Config.RewardAmount

local function GetOnlineCops()
  local players = QBCore.Functions.GetPlayers()
  local count = 0
  for _, id in pairs(players) do
    local player = QBCore.Functions.GetPlayer(id)
    if player and player.PlayerData.job.name == 'police' then count = count + 1 end
  end
  return count
end

QBCore.Functions.CreateCallback('heist:canStart', function(source, cb)
  if Heist.active then return cb(false, 'Heist already active') end
  if os.time() < Heist.cooldown then return cb(false, 'On cooldown') end
  if GetOnlineCops() < REQUIRED_COPS then return cb(false, 'Not enough cops') end
  return cb(true)
end)

RegisterNetEvent('heist:start', function()
  local src = source
  QBCore.Functions.TriggerCallback('heist:canStart', src, function(allowed, reason)
    if not allowed then
      TriggerClientEvent('heist:notify', src, reason)
      return
    end
    Heist.active = true
    Heist.cooldown = os.time() + COOLDOWN
    -- Broadcast to clients
    TriggerClientEvent('heist:beginClient', -1, {position = Config.HeistPos})
    -- Example: schedule reward when complete, ensure server-side checks on 'complete' event
  end)
end)

RegisterNetEvent('heist:complete', function(proof)
  local src = source
  -- Validate 'proof' server-side (e.g. verify min duration, server-side timers, and checks)
  if not Heist.active then return end
  -- example simple validation
  if GetOnlineCops() < REQUIRED_COPS then
    TriggerClientEvent('heist:notify', src, 'Heist failed: police left')
    Heist.active = false
    return
  end
  Heist.active = false
  -- Grant reward safely
  local xPlayer = QBCore.Functions.GetPlayer(src)
  if xPlayer then
    xPlayer.Functions.AddMoney('cash', REWARD, 'heist-reward')
    TriggerClientEvent('heist:notify', src, 'You got $' .. REWARD)
  end
end)

Client example (client.lua)

Client should only request actions and play animations/UI. Do not directly add money or change server state.

RegisterNetEvent('heist:beginClient', function(data)
  -- show UI, start timers, lock doors locally
  -- send 'heist:start' event when player interacts
end)

-- Start interaction (e.g. qb-target or keypress)
function AttemptStart()
  TriggerServerEvent('heist:start')
end

Security & validation checklist

Follow these checks before releasing the script:

StepWhy it matters
Server-side rewardPrevents item/money forging from clients
Cooldown enforced server-sideStops rapid repeated rewards
Police count validated server-sideKeeps intended difficulty and balance
Event rate-limitingReduce spam and brute-force attempts
Sanitize inputsAvoid injection or malformed state updates
Log failuresHelps detect exploits and debug

Testing and deployment

  1. Local test with dev players: verify start, abort, complete flows.
  2. Simulate low/high police counts and check server rejection messages.
  3. Attempt client-side spoofing (mock events) to verify server denies illicit rewards.
  4. Monitor server logs for unexpected states and add guards accordingly.
  5. When ready, deploy to a staging server and run a short stress test before main server.

Integration tips

If you have qb-target, expose an interaction export and register the target zone. If you use ox_lib, move UI calls into ox_lib dialog flows but keep validation on the server. Keep optional integrations behind feature flags in config.lua so installation is simple for other servers.

Practical checklist (quick)

  • Create config.lua with REWARD, COOLDOWN, REQUIRED_COPS
  • Implement server.lua with strict validation and logs
  • Keep client.lua visual-only and network-safe
  • Test edge cases and logging
  • Offer admin commands to reset state and inspect cooldown

Closing notes

Security-first design and server-side authority are the keys to a reliable heist script. Start small, validate frequently, and keep UI/animation concerns on the client. Use the checklist and code patterns above as a base, adapt to your framework (ESX or ox_lib) by replacing the QBCore calls, and always test attack paths before going live.
