QBCore Lawyer Job — Build a secure, server-authoritative Lawyer role for FiveM (+ Roblox notes)

Updated September 2026 · 8 min read · Stellar AI

This guide helps you create a secure, playable Lawyer job for QBCore servers, including server-side validation, qb-target points, invoice handling, and a compact Roblox pattern for translating similar workflows. Follow the file layout, install steps, and security notes to avoid common pitfalls.

Why server authority matters

Lawyer gameplay touches money, player records, and case state. That means all authoritative operations — issuing invoices, paying fees, modifying case records — must run on the server. The client should only request actions and present UI. Below you'll find a minimal QBCore resource layout, a client-target example using qb-target, server validation for payroll/invoices, and a short Roblox pattern for similar UIs using RemoteEvents and safe DataStore access.

Implementation plan (short)

  • Create a QBCore resource named qb-lawyer with fxmanifest, client.lua, server.lua, and config.lua.
  • Register qb-target zones to open case UI and show lawyer-only actions.
  • Implement server-side handlers for invoices, payments, and record changes using QBCore.Functions.GetPlayer and Player.Functions.AddMoney.
  • Validate all client requests on the server and log critical events.
  • Optional: mirror concept on Roblox with RemoteEvents + DataStore and pcall retry.

Assumptions and dependencies

  • QBCore v1/v2 style core available via exports['qb-core']:GetCoreObject(). Adjust names if your core differs.
  • qb-target present for zone interactions. If using ox_target or a different targeting system adapt the target registration call.
  • Roblox readers assume standard ServerScriptService, ReplicatedStorage for RemoteEvents, and use of DataStoreService.

Minimal QBCore example (safe, server-authoritative)

This example demonstrates a server-side handler for creating an invoice and a client registration for qb-target. The server validates the caller's job and player funds before applying money operations.

-- fxmanifest.lua
fx_version 'cerulean'
game 'gta5'
author 'you'
description 'QBCore Lawyer Job'
version '1.0.0'
shared_script 'config.lua'
client_script 'client.lua'
server_script 'server.lua'

-- server.lua
local QBCore = exports['qb-core']:GetCoreObject()

RegisterNetEvent('qb-lawyer:server:CreateInvoice', function(targetPlayerId, amount, reason)
    local src = source
    local creator = QBCore.Functions.GetPlayer(src)
    if not creator then return end

    -- only lawyers can create invoices
    if creator.PlayerData.job == nil or creator.PlayerData.job.name ~= 'lawyer' then
        TriggerClientEvent('QBCore:Notify', src, 'Not authorized', 'error')
        return
    end

    amount = tonumber(amount) or 0
    if amount <= 0 or amount > 100000 then
        TriggerClientEvent('QBCore:Notify', src, 'Invalid amount', 'error')
        return
    end

    local target = QBCore.Functions.GetPlayer(targetPlayerId)
    if not target then
        TriggerClientEvent('QBCore:Notify', src, 'Player not found', 'error')
        return
    end

    -- create invoice server-side (example uses qb-billing if present)
    TriggerClientEvent('QBCore:Notify', target.PlayerData.source, 'You received an invoice: $'..amount, 'info')
    -- If you integrate qb-billing, call its server event here instead of direct money ops
    -- Log and persist the invoice in your database if needed
end)

-- client.lua (register qb-target)
local lawyerDeskCoords = vector3(200.0, -900.0, 30.0) -- example

Citizen.CreateThread(function()
    exports['qb-target']:AddBoxZone('lawyer_desk', lawyerDeskCoords, 1.2, 1.2, {
        name = 'lawyer_desk', heading = 0, debugPoly = false
    }, {
        options = {
            { event = 'qb-lawyer:client:OpenMenu', icon = 'fas fa-gavel', label = 'Open Case File', job = 'lawyer' }
        },
        distance = 2.5
    })
end)

RegisterNetEvent('qb-lawyer:client:OpenMenu', function()
    -- open NUI or menu to create invoice; client only sends intent to server
    -- sample: TriggerServerEvent('qb-lawyer:server:CreateInvoice', targetId, amount, reason)
end)

Roblox pattern: server-authoritative case updates + DataStore safety

On Roblox, the server must own case state and DataStore writes. The client sends a request via RemoteEvent; the server validates the player's role and writes to DataStore using pcall with retries.

-- ServerScript (ServerScriptService)
local Replicated = game:GetService('ReplicatedStorage')
local DataStoreService = game:GetService('DataStoreService')
local CasesStore = DataStoreService:GetDataStore('LawyerCases')
local ClaimEvent = Replicated:WaitForChild('LawyerClaimCase')

local function safeSave(key, value)
    for i = 1, 3 do
        local success, err = pcall(function()
            CasesStore:SetAsync(key, value)
        end)
        if success then return true end
        wait(0.5 * i) -- exponential-ish backoff
    end
    return false
end

ClaimEvent.OnServerEvent:Connect(function(player, caseId)
    -- validate player's role (example uses a BoolValue on player)
    local isLawyer = player:FindFirstChild('IsLawyer') and player.IsLawyer.Value
    if not isLawyer then
        -- don't reveal details; send benign rejection
        ClaimEvent:FireClient(player, false, 'Not authorized')
        return
    end

    local key = 'case_' .. tostring(caseId)
    local success = safeSave(key, {claimedBy = player.UserId, time = os.time()})
    if success then
        ClaimEvent:FireClient(player, true, 'Case claimed')
    else
        ClaimEvent:FireClient(player, false, 'DataStore error. Try later')
    end
end)

Install & testing notes

For FiveM: drop the qb-lawyer folder in resources and add it to server.cfg or ensure it's started via txAdmin. Start with the console log enabled and try actions as a non-lawyer and lawyer account to confirm server rejections and successful invoice flows.

For Roblox: place the RemoteEvent in ReplicatedStorage, the server script in ServerScriptService, and a LocalScript UI in StarterGui to call the RemoteEvent. Test DataStore writes in a development place with proper throttling and avoid spamming writes during tests.
