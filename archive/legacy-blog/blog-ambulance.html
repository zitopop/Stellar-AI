Building a Robust QBCore Ambulance Job — Server-Authoritative Design

Updated September 2026 · 8 min read · Stellar AI

This guide walks a developer through planning and building a server-authoritative ambulance job for QBCore: features, file layout, secure server-side checks, client interactions, qb-target and ox_lib considerations, and a practical checklist to ship a maintainable resource.

Overview

An ambulance job is more than animations and props: it is a server-authoritative workflow for player health, treatments, billing, and vehicles that must resist exploitation while providing a responsive UX. This guide presumes QBCore as the framework and shows safe patterns for server validation, event design, and integrating common FiveM extensions like qb-target and ox_lib.

Implementation plan (short)

  • Define job features and permissions (revive, treat, tow, bill).
  • Create file layout and fxmanifest.
  • Implement server events and callbacks with strong validation.
  • Add client UI and target interactions (qb-target / ox_target).
  • Test edge cases and anti-cheat scenarios.

Assumptions & dependencies

  • Server uses QBCore framework (qb-core) and MySQL (or equivalent) for persistent data.
  • qb-target or ox_target for in-world interactions; ox_lib optional for notifications and progress bars.
  • Developers will run updates on a dev server and preserve existing database schemas.

Core design principles

Keep authority on the server. Clients may request actions, but the server must verify:

  • Player job and rank (is the caller an active ambulance).
  • Distance checks for target players and vehicles.
  • Cooldowns and rate limits to prevent spam.
  • Database updates (billing, job logs) must happen server-side.

Key features to implement

  • Revive: validate target is downed, within range, and not already revived.
  • Treat: apply temporary buffs/debuffs, change health and armour via server events.
  • Ambulance vehicle management: spawn, store, and impound handling with server records.
  • Billing and payments: create an invoice server-side and log to DB; never trust client amounts.
  • Dispatch and on-duty toggles: toggle duty on server and allow commands for restricted roles.

File layout and fxmanifest example

Keep files organized to make authority clear.

  'client/main.lua'

}

Server-side example: revive with validations

Always check job, distance, and target state.

-- server/main.lua (snippet)
local QBCore = exports['qb-core']:GetCoreObject()

QBCore.Functions.CreateCallback('ambulance:server:canRevive', function(source, cb, targetId)
  local src = source
  local Player = QBCore.Functions.GetPlayer(src)
  local targetPlayer = QBCore.Functions.GetPlayer(targetId)
  if not Player or not targetPlayer then return cb(false, 'Invalid player') end

  if Player.PlayerData.job.name ~= 'ambulance' then
    return cb(false, 'Not Ambulance')
  end

  local srcCoords = GetEntityCoords(GetPlayerPed(src)) -- server utility needed via client? store last known coords server-side or trust a ranged check
  local tgtCoords = targetPlayer.PlayerData.coords -- if you store coords periodically on server
  if #(srcCoords - tgtCoords) > 3.5 then
    return cb(false, 'Too far')
  end

  if not targetPlayer.PlayerData.metadata.isDown then
    return cb(false, 'Target not down')
  end

  -- Passed checks
  cb(true)
end)

RegisterNetEvent('ambulance:server:revive', function(targetId)
  local src = source
  QBCore.Functions.TriggerCallback('ambulance:server:canRevive', src, function(ok, err)
    if not ok then
      TriggerClientEvent('QBCore:Notify', src, err or 'Cannot revive', 'error')
      return
    end
    local targetPlayer = QBCore.Functions.GetPlayer(targetId)
    if targetPlayer then
      -- perform revive: reset metadata and health on server
      targetPlayer.Functions.SetPlayerData('metadata', { isDown = false })
      TriggerClientEvent('ambulance:client:applyRevive', targetId)
      -- optional: log revive in DB
    end
  end, targetId)
end)

Client-side interactions (qb-target)

Client triggers must call secure server callbacks instead of directly applying effects.

-- client/main.lua (snippet)
exports['qb-target']:AddTargetBone('player', {
  options = {
    {
      type = 'client',
      event = 'ambulance:client:attemptRevive',
      icon = 'fas fa-hand-holding-medical',
      label = 'Revive'
    }
  },
  distance = 3.5
})

RegisterNetEvent('ambulance:client:attemptRevive', function(data)
  local targetId = data.entityId -- ensure qb-target supplies ID in your config
  QBCore.Functions.TriggerCallback('ambulance:server:canRevive', function(ok)
    if ok then
      TriggerServerEvent('ambulance:server:revive', targetId)
    else
      QBCore.Functions.Notify('Cannot revive', 'error')
    end
  end, targetId)
end)

Billing, DB writes and persistence

Create invoices server-side. Never accept an amount from the client. Instead, define cost tables in config.lua and reference them server-side when creating a bill or adding a DB record.

Anti-cheat & validation checklist

TestExpected server-side control
Revive spamCooldowns and rate limits on server
Unauthorized reviveVerify player job and rank
Distance exploitsServer-calculated distance or frequent server-side position updates
Billing tamperingServer uses config costs, logs to DB

Practical deployment checklist

  1. Create a dev branch and back up your DB schema.
  2. Install resource and fxmanifest; verify dependencies (qb-core, qb-target, oxmysql).
  3. Run through server-side validation tests and log every decision path.
  4. Test with two players: ambulance and patient; validate distances, revives, and bills.
  5. Check edge cases: disconnect during revive, duplicate events, DB failures.
