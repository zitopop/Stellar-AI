Server-authoritative RP best practices

FiveM Roleplay Server Tips: Practical Guidance for Reliable RP Systems

Updated September 2026 · 8 min read · Stellar AI

This guide collects pragmatic tips that senior FiveM builders use to keep roleplay servers stable, secure, and fun. It focuses on server authority, validation patterns for QBCore and ESX, common performance traps, and a small ready-to-install example that demonstrates safe item purchases and validation.

1. Start with a clear plan

Every successful RP feature begins with a short implementation plan: purpose, actors (player, admin, job), data sources (database, player meta), and failure modes (network loss, DataStore failure equivalent for FiveM). Write two-sentence acceptance criteria: what must work from the player's perspective and what must be validated server-side. Keep the first iteration minimal — a single-server-authoritative flow you can test end-to-end.

2. Enforce server authority — always

Client scripts are for UI, animations, and local effects. Anything affecting economy, items, permissions, or persistent state must be performed and validated on the server. Use server events or callbacks that check player identity, money, item amounts, job, and permissions before mutating state. For QBCore, use QBCore.Functions.GetPlayer and Player.Functions.RemoveMoney/AddItem on the server; for ESX, use xPlayer functions server-side. Never trust values passed from the client.

Example principles

  • Client -> Server: request purchase or action (no item giving, no money removal).
  • Server: validate cost, check player balance and inventory space, perform transaction, then notify client.
  • Log suspicious repeated failures and rate-limit requests.

3. Resource structure and manifest

Keep a predictable resource layout: fxmanifest.lua, config.lua, server.lua, client.lua, and a modules folder for shared functions. Declare explicit dependencies in fxmanifest.lua to ensure startup ordering (qb-core, ox_lib, qb-target, etc.). Example and full files are shown below.

4. Validation patterns (QBCore & ESX)

QBCore pattern (server):

local QBCore = exports['qb-core']:GetCoreObject()
RegisterNetEvent('rpshop:server:buy', function(item, qty)
  local src = source
  local Player = QBCore.Functions.GetPlayer(src)
  local price = Config.Items[item] and Config.Items[item].price * qty or nil
  if not price then return end
  if Player and Player.Functions.RemoveMoney('cash', price) then
    Player.Functions.AddItem(item, qty)
    TriggerClientEvent('QBCore:Notify', src, 'Purchase successful')
  else
    TriggerClientEvent('QBCore:Notify', src, 'Not enough money', 'error')
  end
end)

ESX has analogous server checks. The key is atomic server-side checks and changes — never remove money on the client or assume the client will add the item.

5. Use qb-target and ox_lib for UX but keep logic server-side

qb-target and ox_lib help surface interactions; they run on the client to detect player context. When a player interacts, send a lightweight request to the server. Avoid sending rich state from client to server; pass only identifiers and quantities and let the server resolve prices and permission checks.

6. Performance and resource limits

Keep tick work minimal. Long loops, heavy math, or synchronous DB operations should run on the server in controlled coroutines. Use exports and callbacks efficiently. Limit use of global timers; prefer event-driven flows. Prefetch static config data into memory on startup rather than querying DB on every player action.

7. Anti-cheat and audit

Design your server to detect anomalies: impossible inventory amounts, rapid repeated purchases, or inconsistent balances between subsystems. Store an audit trail for sensitive actions (player, action, old_balance, new_balance, timestamp) and rotate logs. Rate-limit client requests and verify key state again before committing.

8. Testing and deployment

Test features on a local or staging server with realistic player flows. Use at least one dedicated test account with admin disabled to validate permission boundaries. When deploying: update one server at a time, monitor logs, and have a rollback plan (resource stop/start and DB transaction rollback if needed).

10. Small installable example: safe shop (QBCore)

Implementation plan: a tiny resource named rp_shop that provides a server-authoritative purchase flow. Assumptions: QBCore v2-style GetCoreObject export is available and ox_lib/qb-target are present. Files below are complete and destination-labelled.

Files included

  1. fxmanifest.lua — declares dependencies
  2. config.lua — item list and prices
  3. server.lua — authoritative purchase handling
  4. client.lua — UI trigger and qb-target integration

Where to place: put the folder rp_shop in your server resources directory and add ensure rp_shop to server.cfg. Do not include secrets. Restart the server or start the resource.

Installation and validation steps

  1. Ensure dependencies are installed (qb-core, qb-target, ox_lib).
  2. Add resource to server.cfg and start it.
  3. Use a non-admin test account to attempt purchases, check balances and added items.
  4. Review server console for logged purchase actions and errors.

11. Security considerations

Never expose developer keys or DB credentials in resources. Limit admin commands, validate permissions server-side, and avoid long-running synchronous DB calls on the main server thread. If you must perform heavy DB work, queue it and perform in controlled worker threads or background tasks.

12. Monitoring, iteration, and next steps

After launch, collect errors, suspicious transaction rates, and player feedback. Iterate on UX (qb-target hints, ox_lib menus). For larger systems, consider modularizing services: an economy service, an inventory service, and job service with clear export APIs and access controls.
