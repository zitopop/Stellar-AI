ox_lib not working? Fix the dependency before blaming the script.

When ox_lib menus, notifications, callbacks or input dialogs do not work, the issue is usually resource order, manifest setup, import syntax, context or a missing shared script line.

Confirm ox_lib starts before anything that uses it

ox_lib is a dependency. If another resource calls lib functions before ox_lib is ready, the problem may appear as a nil value, missing export, menu not opening or notification doing nothing. Put ox_lib high in your start order, above resources that use menus, progress bars, callbacks, context menus, zones or notifications. Then restart the server and read the first fresh error instead of relying on old console output.

ensure ox_lib
ensure qb-core
ensure my-menu-resource

If the resource still fails after reordering, restart the dependent resource after ox_lib is already running. A clean boot and a manual restart can reveal whether the issue is startup order or the code itself.

Check the manifest import

Many ox_lib examples require the init file to be loaded by the resource manifest. If the manifest does not include the correct shared script, the global lib object may not exist where your client or server code expects it. Check the exact path used by the current ox_lib version installed on your server. Do not copy an old snippet without confirming it matches your installed files.

shared_scripts {
  '@ox_lib/init.lua',
  'config.lua'
}

The order matters. Config and init files should load before code that reads them. If a script uses lib in a client file, the client must have access to the import. If a server file uses lib callbacks, the server side must load what it needs too.

Separate client features from server features

Some ox_lib features are meant for client-side UI. Menus, input dialogs and notifications are normally client-facing. Server code can validate state and then tell the client to open UI, but server files cannot directly show a local player interface in the same way a client file can. If a menu does not open, check whether the call is being made from the right context. If a notification never appears, confirm the player client receives the event that should show it.

Callbacks and server-side checks should still be authoritative. Do not move trusted economy, inventory or permission logic to the client just because a UI call is client-side. Keep rewards, purchases and job permissions on the server, then use ox_lib UI to display the result.

Watch for old or mixed examples

FiveM guides, Discord snippets and old resources often mix different framework versions. Some examples assume QBCore, some assume ESX, and some are standalone. A menu example may work by itself but fail when combined with inventory exports, target zones or job checks. Before adding framework logic, make the smallest ox_lib example work in your server environment. Then add the QBCore or ESX-specific checks one step at a time.

Inspect the first console error

Read both the FXServer console and the F8 client console. If the server says an export is missing, check dependency order and resource name. If the client says lib is nil, check the manifest import and the script side. If no error appears but the menu does not open, add prints before and after the call so you know whether the code path runs.

A silent failure is often not ox_lib itself. It may be a target option that never fires, a job condition that rejects the player, a missing item check, an outdated event name or a UI script that never loads. Prove the code path before changing the library setup.

Use a minimal test resource

Create or isolate a tiny resource that only loads ox_lib and shows one notification or simple context menu. If that works, ox_lib is installed correctly and the bug is in the larger resource. If the tiny resource fails, focus on installation, manifest and start order. This keeps your diagnosis clean and stops you from editing gameplay code for a dependency problem.
