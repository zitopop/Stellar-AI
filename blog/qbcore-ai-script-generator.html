QBCore AI script generator: jobs, events and server-side checks

A practical workflow for generating QBCore jobs and systems while keeping server authority, framework assumptions and testing visible.

Stellar AI · Updated 19 September 2026 · 5 min read

QBCore makes it convenient to work with players, jobs, money and metadata, but that convenience does not remove the need for server authority. When you use AI to build a QBCore resource, the useful question is not only whether it can write Lua, but whether the resource keeps trust boundaries clear and fits the framework your server actually runs.

1. Define the job or system as state transitions

For a mechanic job, a player might go on duty, inspect a vehicle, consume a repair item, complete an animation and receive a server-approved result. Writing these transitions first gives the AI something testable to implement.

2. Keep QBCore object usage on the correct side

Client code can read local player data for presentation, but server code should own authoritative job checks, money changes and item transactions. Do not let a client send a final payout or claim it owns an item without verification.

3. Make event validation part of the prompt

State which values a client may request and which values the server must calculate or verify. Treat job state, item ownership, payment amounts, cooldowns and completion state as server-authoritative.

4. Keep framework assumptions visible

QBCore servers differ. Inventory resources, target libraries, notification systems and database patterns vary. Ask the AI to list assumptions instead of silently choosing an implementation.

5. Separate configuration from logic

Locations, grades, item names, prices and cooldowns usually belong in configuration. Business logic should read those values rather than scattering magic numbers through client and server files.

6. Test the resource privately

  • Test with the correct job and without it.
  • Test while on duty and off duty.
  • Trigger network events repeatedly.
  • Test missing inventory and resource restarts.
  • Test two players using the same state.

7. Write a stronger first prompt

State the QBCore version and integrations you actually use, list the files you want returned, identify every privileged action, and ask for server-side validation plus a short install and test checklist.

8. Preserve project context

The second and third change to a resource are often harder than the first generation. Keep the existing structure when bringing back a bug, changing a dependency or adding a feature.

9. Think about abuse cases before polish

If a job pays money, assume someone will try to trigger the payout event without doing the job. Ask what the client sends, what the server verifies, what state changes, and what happens on a duplicate or malformed request.

10. Keep logs useful, not noisy

Log unexpected state, missing dependencies and rejected high-value actions where appropriate, but avoid printing every normal interaction.

11. Plan framework upgrades

Keep direct framework and integration calls concentrated where practical so inventory, target or QBCore changes are easier to update.

12. Release checklist

  • Network events have server-side validation.
  • Job, grade and duty checks use current server state.
  • Money and items cannot be awarded twice from one action.
  • Dependencies and configuration are documented.
  • Resource restart and multiple-player behaviour have been tested.

13. Separate framework integration from game rules

A useful QBCore request separates framework operations—finding a player, inspecting a job, updating an item—from your server's own rules such as eligible grades, locations, cooldowns and reward ranges. That makes generated code easier to review and adapt.

For example, a delivery job should not accept a reward amount supplied by the client. The server should look up the active assignment, check progress and calculate the reward from server configuration.

14. Review the result before adding more scope

Read the manifest and installation notes, confirm named dependencies exist, inspect server event handlers, then test one job from start to finish, cancel it halfway, reconnect and try to finish it twice. Save the working version before adding more scope.

Before release, compare every privileged client request with the server checks that authorize it. This final pass catches missing job, inventory, distance, cooldown, and duplicate-action validation before players can reach the resource.
